## 1. 项目定位：GustoBot 是什么？

### 1.1 解决什么问题

中华菜谱知识体系庞大且复杂——八大菜系的地域特色、食材搭配的营养学原理、烹饪技法的代际传承、历史典故的文化内涵，这些内容既有高度结构化的部分（食材用量、烹饪步骤），也有大量非结构化的经验性描述。传统关键词搜索难以满足用户对菜谱知识的深度探索需求。

GustoBot 要解决的核心问题是：**如何让用户通过自然语言与菜谱知识进行深度交互？**

不只是简单的问答（"宫保鸡丁怎么做？"），还包括：
- 关系推理（"哪些菜用到了花椒？"）
- 统计分析（"川菜有多少道菜？"）
- 文化探索（"宫保鸡丁的典故是什么？"）
- 图片识别（上传一张菜品照片，识别是什么菜）
- 文件分析（上传 Excel 文件，分析其中的菜谱数据）

### 1.2 面向谁

| 角色 | 使用场景 |
|------|---------|
| 普通用户 | 日常做菜时查询菜谱、了解食材搭配、获取营养建议 |
| 美食爱好者 | 探索菜系文化、了解历史典故、发现新菜品 |
| 开发者 | 作为垂直领域智能客服的模板，迁移到其他领域（中医药典、法律咨询等） |

### 1.3 核心价值主张

GustoBot 不是一个简单的聊天机器人，而是一个 **可迁移、可扩展的垂直领域智能客服模板系统**。通过清晰的三层架构设计，只需更换知识源与图谱结构，即可迁移到其他垂直领域。

### 关键目录说明

**`gustobot/` 的分层架构**采用经典的整洁架构（Clean Architecture）思想：

| 层 | 目录 | 职责 |
|----|------|------|
| 接口层 | `interfaces/` | HTTP 路由定义、请求参数校验、响应格式化 |
| 应用层 | `application/` | 业务服务编排、Agent 工作流定义 |
| 领域层 | `domain/` | 业务实体、值对象、领域逻辑 |
| 基础设施层 | `infrastructure/` | 数据库连接、外部 API 调用、缓存实现 |
| 配置层 | `config/` | 全局配置加载 |

这种分层使得业务逻辑与技术实现解耦，便于测试和迁移。

**`kb_ingest/` 是独立微服务**：它有自己的 `main.py` 和 `Dockerfile`，专门负责知识库数据的导入（Excel 解析、文本切分、向量化），通过 HTTP API 与主服务通信。

## 5. 配置体系

### 5.1 settings.py 的加载机制

GustoBot 使用 **Pydantic Settings** 管理所有配置，这是整个应用配置的核心。

`gustobot/config/settings.py` 中的 `Settings` 类继承自 `pydantic_settings.BaseSettings`：

```python
class Settings(BaseSettings):
    # 应用元数据
    APP_NAME: str = "GustoBot"
    APP_VERSION: str = "0.1.2"
    DEBUG: bool = True

    # ... 其他字段 ...

    model_config = {
        "env_file": ".env",       # 从 .env 文件加载
        "case_sensitive": True,    # 变量名大小写敏感
        "extra": "ignore"          # 忽略 .env 中未定义的变量
    }

settings = Settings()  # 模块级单例，整个应用共享
```

**加载优先级**（从高到低）：
1. 系统环境变量（`export LLM_MODEL=xxx`）
2. `.env` 文件中的变量
3. 代码中的 `default` 值

**关键特性**：
- **AliasChoices（别名兼容）**：例如 `LLM_MODEL` 同时支持 `OPENAI_MODEL` 作为别名，方便从不同 LLM 迁移
- **property 兼容层**：通过 `@property` 定义 `OPENAI_API_KEY` 等属性，实际指向 `LLM_API_KEY`，保持向后兼容
- **类型安全**：Pydantic 会自动校验类型，比如 `PORT: int = 8000`，如果 .env 中写了非数字会报错

## 7. 为什么需要 Agent 而不是简单 RAG？

这是理解 GustoBot 架构设计的关键问题。

### 7.1 简单 RAG 的局限

简单 RAG（检索增强生成）的流程是：用户提问 → 向量检索 → 拼接上下文 → LLM 生成回答。

这种方式存在几个根本性问题：

**问题 1：无法处理不同类型的查询**

用户可能问完全不同类型的问题：
- "宫保鸡丁怎么做？" → 需要查询菜谱的步骤数据
- "川菜有多少道？" → 需要 SQL 聚合统计
- "宫保鸡丁的典故" → 需要语义检索长文本
- "哪些菜用到了花椒？" → 需要图数据库关系查询
- 上传一张菜品图片 → 需要 Vision 模型识别

简单 RAG 只有一条检索路径，无法区分这些需求。

**问题 2：无法分解复杂任务**

用户问"帮我找几道不用辣椒的川菜，并说明它们的历史"，这需要：
1. 查询图数据库找出不用辣椒的川菜
2. 为每道菜检索历史典故
3. 融合结果生成回答

简单 RAG 无法将这个任务拆解为多个子任务并行执行。

**问题 3：无法保证答案质量**

简单 RAG 检索到的内容可能质量参差不齐，缺乏：
- 安全防护（拒绝超出范围的问题）
- 结果精排（Reranker 二次过滤）
- 多源融合（综合多个数据源的结果）

### 7.2 Agent 架构的优势

GustoBot 的三层 Multi-Agent 架构解决了上述所有问题：

```
L1 主路由层：意图识别 → 自动选择最优处理路径
    ↓
L2 多工具子图层：Guardrails 安全检查 → Planner 任务分解 → 并行工具调用
    ↓
L3 原子工具层：Neo4j / MySQL / Milvus / PostgreSQL / 外部搜索
```

**核心优势**：

| 能力 | 简单 RAG | GustoBot Agent |
|------|---------|----------------|
| 意图识别 | 无 | L1 启发式 + LLM 双重路由 |
| 工具选择 | 固定检索 | L2 根据任务动态选择工具 |
| 任务分解 | 不支持 | Planner Map-Reduce 模式 |
| 并行执行 | 不支持 | 多个工具节点并行调用 |
| 安全防护 | 无 | Guardrails 节点拒绝越界查询 |
| 结果精排 | 无 | Reranker 双阈值过滤 |
| 多源融合 | 单源 | Summarize 节点聚合多工具结果 |
| 可扩展性 | 差 | 添加新工具只需注册到 Tool Selection |

## 8. 为什么同时用多种数据库？

GustoBot 使用了 5 种不同的数据存储：Neo4j、MySQL、Milvus、PostgreSQL pgvector、Redis。这看起来很复杂，但每种数据库都有不可替代的角色。

### 8.1 数据特性决定存储选型

| 数据类型 | 示例 | 特征 | 最佳存储 |
|---------|------|------|---------|
| 关系图谱 | 菜品-食材-菜系的关系网络 | 多对多关系、需要图遍历 | **Neo4j** |
| 结构化表格 | 菜谱列表、营养成分表 | 固定 Schema、需要聚合统计 | **MySQL** |
| 长文本语义 | 历史典故、文化故事 | 非结构化、需要语义检索 | **Milvus** |
| 结构化向量 | 菜谱名称、菜系枚举值 | 结构化 + 需要向量检索 | **PostgreSQL pgvector** |
| 缓存 | 对话历史、语义缓存 | 高频读写、需要 TTL | **Redis** |

### 8.2 各数据库的具体用途

**Neo4j（图数据库）**
- 存储：菜谱、食材、菜系、烹饪方法等实体及其关系
- 查询语言：Cypher（如 `MATCH (r:菜谱)-[:使用]->(i:食材 {name: '花椒'}) RETURN r`）
- 优势：处理"哪些菜用到了花椒"这类关系查询，比 SQL 的 JOIN 高效得多
- 工具节点：`cypher_query`（动态生成 Cypher）、`predefined_cypher`（预定义查询模板）

**MySQL（关系型数据库）**
- 存储：结构化的菜谱数据表
- 查询方式：Text2SQL，LLM 将自然语言转为 SQL
- 优势：处理"川菜有多少道"这类统计聚合查询
- 工具节点：`text2sql_query`

**Milvus（向量数据库）**
- 存储：长文本（典故、故事）的 Embedding 向量
- 查询方式：向量相似度检索
- 优势：处理语义模糊的查询，如"关于春节的菜谱故事"
- 角色：作为 PostgreSQL 的兜底，当结构化检索无结果时使用

**PostgreSQL pgvector（结构化向量库）**
- 存储：结构化字段（菜谱名称、菜系等）的向量
- 查询方式：结构化查询 + 向量相似度
- 优势：对结构化数据的检索比纯向量库更精准
- 角色：知识库检索的第一优先级（PostgreSQL 优先策略）

**Redis（缓存）**
- 存储：对话历史、语义缓存
- 查询方式：Key-Value + TTL 过期
- 优势：毫秒级读写，自动过期清理
- 配置：`REDIS_CACHE_EXPIRE=43200`（12 小时）、`REDIS_CACHE_THRESHOLD=0.92`（语义缓存相似度阈值）

### 8.3 PostgreSQL 优先兜底策略

知识库检索的流程体现了多数据库协作的精髓：

```
用户提问（历史典故类）
    ↓
Step 1: 查询 PostgreSQL pgvector（结构化数据，快速精准）
    ↓
有结果？ → 是 → 直接使用，跳过 Milvus
    ↓ 否
Step 2: 查询 Milvus（长文本语义检索，兜底）
    ↓
Step 3: 可选 — 调用外部搜索 API（补充最新知识）
    ↓
Reranker 精排 → 双阈值过滤 → 返回最终结果
```

这种分层策略确保了检索的精度和覆盖率。
