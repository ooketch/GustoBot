## 9.1 Docker 服务拓扑

GustoBot 的 `docker-compose.yml`（位于项目根目录）定义了 **10 个服务**，分为 4 个功能层：

### 服务总览

| 服务 | 镜像 / 构建目标 | 宿主端口 : 容器端口 | 职责 |
|---|---|---|---|
| `backend` | Dockerfile `server` 阶段 | 8000:8000 | FastAPI 主服务，承载聊天、路由、Agent 调度 |
| `neo4j` | Dockerfile `neo4j_seeded` 阶段 | 17474:7474, 17687:7687 | 图数据库，存储菜谱知识图谱（Dish/Ingredient/Flavor 等节点） |
| `mysql` | mysql:8.0 | 13306:3306 | 关系数据库，存储结构化菜谱数据 |
| `redis` | redis:7-alpine | 6379:6379 | 缓存层：语义缓存（相似问题命中率）、会话历史 |
| `milvus` | milvusdb/milvus:v2.3.3 | 19530:19530, 9091:9091 | 向量数据库，存储菜谱文本的 embedding |
| `etcd` | quay.io/coreos/etcd:v3.5.5 | (无外部端口) | Milvus 的元数据存储依赖 |
| `minio` | minio/minio | 9000:9000, 9001:9001 | Milvus 的对象存储依赖 |
| `kb_postgres` | ankane/pgvector | 5433:5432 | 知识库专用 PostgreSQL，带 pgvector 扩展 |
| `kb_ingest` | kb_ingest/Dockerfile | 8100:8000 | 知识库数据摄取服务，处理 Excel 导入、分块、embedding |

### 依赖关系图

```
backend
  ├── neo4j      (图谱查询)
  ├── redis      (缓存/会话)
  └── milvus     (向量检索)
        ├── etcd   (Milvus 元数据)
        └── minio  (Milvus 对象存储)

kb_ingest
  └── kb_postgres (pgvector 存储)
```

### 为什么每个服务都需要存在

- **backend**：核心业务逻辑。用户请求进入后，由 LangGraph Agent 决定走哪条路由（图谱查询、向量检索、Text2SQL、闲聊等）。
- **neo4j**：存储"红烧肉 - 需要 - 五花肉"这类关系三元组。Cypher 查询可以做多跳推理，比如"哪些菜用了花椒且属于川菜"。
- **mysql**：存储结构化字段（菜名、口味、耗时、类型），支持 SQL 聚合统计。
- **redis**：语义缓存——如果两个问题的 embedding 余弦相似度超过 0.92，直接返回缓存结果，省一次 LLM 调用。同时存储对话历史（TTL 3 天）。
- **milvus + etcd + minio**：Milvus 是向量数据库，负责"相似文本召回"。etcd 和 minio 是 Milvus standalone 模式的内部依赖，不直接被业务代码访问。
- **kb_postgres + kb_ingest**：独立的知识库子系统。kb_ingest 负责把 Excel/文本切块后写入 pgvector；backend 查询时通过 HTTP 调用 kb_ingest 或直接查 kb_postgres。

### 网络与卷

所有服务通过 `gustobot-network`（bridge 网络）互通。服务间通过服务名（如 `redis`、`neo4j`）互相访问。

数据卷用于持久化：

| 卷名 | 对应服务 | 用途 |
|---|---|---|
| `neo4j_data` | neo4j | 图数据库持久化 |
| `mysql_data` | mysql | 关系数据持久化 |
| `redis_data` | redis | RDB 持久化 |
| `milvus_data` | milvus | 向量数据持久化 |
| `etcd_data` | etcd | 元数据持久化 |
| `minio_data` | minio | 对象存储持久化 |
| `kb_pgdata` | kb_postgres | 知识库 PostgreSQL 持久化 |

此外，backend 还通过 bind mount 挂载了 `./gustobot`、`./data`、`./uploads` 和 `./.env`，方便开发时热更新。

## 9.2 Dockerfile 构建流程

`Dockerfile` 定义了两个构建阶段（multi-stage build）：

### 阶段一：server（后端服务）

```
python:3.10-slim
  ├── 安装 build-essential（编译 C 扩展依赖）
  ├── pip install -r requirements.txt
  ├── 复制 gustobot/、data/、scripts/
  ├── [可选] 构建时初始化 LightRAG（调用 scripts/init_lightrag.py）
  ├── 清除 API Key 环境变量（安全措施）
  └── ENTRYPOINT: backend_entrypoint.sh
      CMD: uvicorn gustobot.main:application --host 0.0.0.0 --port 8000
```

关键设计决策：

1. **国内镜像加速**：使用清华 APT 镜像和中科大 PyPI 镜像，加速国内构建。
2. **构建时初始化 LightRAG**：通过 `INIT_LIGHTRAG_ON_BUILD` 参数控制。如果开启，会在构建阶段调用 LLM 和 Embedding API 把 `data/recipe.json` 的菜谱导入 LightRAG 索引。构建完成后会清除 API Key。
3. **entrypoint 脚本**（`scripts/backend_entrypoint.sh`）：容器启动时依次执行：
   - 检查是否需要自动复制 LightRAG 模板数据
   - 等待 MySQL 就绪（最多 180 秒）
   - 等待 Milvus 就绪（最多 120 秒）
   - 如果 `INIT_KB_MILVUS=true` 且数据文件存在且尚未导入过，执行 `scripts/init_kb_milvus.py` 把知识库数据写入 Milvus
   - 最后 `exec "$@"` 执行 CMD（uvicorn）

### 阶段二：neo4j_seeded（图数据库）

```
neo4j:5.18
  ├── 安装 Python3、APOC 插件
  ├── 复制 recipe.json、excipients.json、recipe_kg 脚本
  ├── 运行 scripts/recipe_kg_to_csv.py 生成节点/关系 CSV
  ├── neo4j-admin database import full 导入图数据
  └── 启动时直接可用，无需运行时导入
```

这个设计的巧妙之处在于：**图数据在构建时就导入完毕**，容器启动后 Neo4j 直接可用，省去了运行时的初始化等待。导入的节点类型包括 Dish、Ingredient、Flavor、CookingMethod、DishType、CookingStep、NutritionProfile、HealthBenefit 共 8 种。

## 9.3 配置体系

### 加载机制

配置核心文件是 `gustobot/config/settings.py`，使用 Pydantic 的 `BaseSettings`：

```python
class Settings(BaseSettings):
    # ... 所有配置项定义 ...

    model_config = {
        "env_file": ".env",      # 自动读取 .env 文件
        "case_sensitive": True,  # 变量名区分大小写
        "extra": "ignore"        # 忽略未声明的环境变量
    }

settings = Settings()  # 模块级单例，整个应用 import 同一个实例
```

加载优先级（高到低）：

1. 系统环境变量（`export` 或 Docker `environment`）
2. `.env` 文件
3. 代码中的 `default` 值

### 关键配置项说明

#### LLM 相关（必须配置）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LLM_PROVIDER` | `openai` | 供应商标识 |
| `LLM_MODEL` | `gpt-4-turbo-preview` | 模型名称 |
| `LLM_API_KEY` | `None` | API 密钥（**必须设置**） |
| `LLM_BASE_URL` | `None` | API 地址（兼容 OpenAI 格式的第三方服务） |

`settings.py` 中定义了 `AliasChoices`，`LLM_API_KEY` 同时接受 `OPENAI_API_KEY`，`LLM_MODEL` 同时接受 `OPENAI_MODEL`，方便从旧配置迁移。

#### Embedding 相关（向量检索必须）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `EMBEDDING_PROVIDER` | `openai` | 供应商 |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | 嵌入模型 |
| `EMBEDDING_DIMENSION` | `1536` | 向量维度，必须与模型匹配 |

#### Reranker 相关（精排）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `RERANK_ENABLED` | `True` | 是否启用精排 |
| `RERANK_PROVIDER` | `custom` | 供应商 |
| `RERANK_MODEL` | `bge-reranker-large` | 精排模型 |
| `RERANK_MAX_CANDIDATES` | `20` | 粗召回候选数 |
| `RERANK_TOP_N` | `6` | 精排后返回数 |

检索流程：Embedding 生成查询向量 -> Milvus 召回 20 条 -> Reranker 精排 -> 返回 Top 6。

#### 数据库连接

| 变量 | 默认值 | 说明 |
|---|---|---|
| `DATABASE_URL` | `sqlite:///./data/gustobot.db` | 关系数据库（Docker 中改为 MySQL） |
| `REDIS_URL` | `redis://localhost:6379/0` | Redis 连接 URI |
| `NEO4J_URI` | `bolt://neo4j:7687` | Neo4j Bolt 协议地址 |
| `MILVUS_HOST` / `MILVUS_PORT` | `localhost` / `19530` | Milvus 地址 |

#### Redis 缓存

| 变量 | 默认值 | 说明 |
|---|---|---|
| `REDIS_CACHE_EXPIRE` | `43200`（12 小时） | 缓存过期时间 |
| `REDIS_CACHE_THRESHOLD` | `0.92` | 语义缓存相似度阈值 |
| `REDIS_CACHE_MAX_SIZE` | `1000` | 每个命名空间最大缓存条目 |

#### LightRAG

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LIGHTRAG_WORKING_DIR` | `./data/lightrag` | 索引存储目录 |
| `LIGHTRAG_RETRIEVAL_MODE` | `hybrid` | 检索模式（local/global/hybrid/naive/mix/bypass） |
| `LIGHTRAG_ENABLE_NEO4J` | `True` | 是否用 Neo4j 做图存储后端 |

#### Agent 行为

| 变量 | 默认值 | 说明 |
|---|---|---|
| `MAX_ITERATIONS` | `10` | Agent 最大迭代次数 |
| `AGENT_TIMEOUT` | `300`（5 分钟） | Agent 超时时间 |
| `CONVERSATION_HISTORY_TTL` | `259200`（3 天） | 对话历史保留时间 |
| `CONVERSATION_HISTORY_MAX_MESSAGES` | `200` | 单会话最大消息数 |

#### 其他

| 变量 | 默认值 | 说明 |
|---|---|---|
| `CORS_ORIGINS` | `http://localhost:3000,http://localhost:5173` | 允许的前端域名 |
| `FILE_UPLOAD_MAX_MB` | `2` | 文件上传大小限制（MB） |
| `ENABLE_EXTERNAL_SEARCH` | `False` | 是否允许联网搜索 |

### 向后兼容设计

`settings.py` 中通过 `@property` 保留了旧变量名的兼容：

```python
@property
def OPENAI_API_KEY(self) -> Optional[str]:
    return self.LLM_API_KEY

@property
def RERANKER_PROVIDER(self) -> str:
    return self.RERANK_PROVIDER
```

这意味着旧代码中使用 `settings.OPENAI_API_KEY` 的地方不会报错。

## 9.7 故障排查

### 问题 1：backend 容器启动后立刻退出

**症状**：`docker compose ps` 显示 backend 状态为 `Exit 1`

**排查步骤**：

```bash
docker compose logs backend
```

**常见原因**：

- `.env` 文件中 `LLM_API_KEY` 未填写。解决：填入有效的 API Key。
- `DATABASE_URL` 指向的 MySQL 尚未就绪。entrypoint 脚本会等待最多 180 秒，如果超时则报错退出。解决：确认 MySQL 容器正常运行。
- `requirements.txt` 中某个包安装失败。解决：检查构建日志，确认网络连通。

### 问题 2：Milvus 启动失败

**症状**：milvus 容器反复重启

**排查步骤**：

```bash
docker compose logs milvus
docker compose logs etcd
docker compose logs minio
```

**常见原因**：

- etcd 或 minio 未就绪。Milvus 依赖这两个服务，Docker Compose 的 `depends_on` 只保证启动顺序，不保证就绪。解决：`docker compose restart milvus`。
- 端口 19530 被占用。解决：修改 `docker-compose.yml` 中的端口映射。

### 问题 3：Neo4j 无数据

**症状**：Neo4j Browser 中查询不到节点

**排查步骤**：

```bash
docker compose exec neo4j cypher-shell -u neo4j -p recipepass \
  -d neo4j "MATCH (n) RETURN labels(n), count(n) LIMIT 10"
```

**常见原因**：

- 构建时 `neo4j-admin database import` 失败。解决：重新构建 `docker compose up -d --build neo4j`。
- 数据卷残留了旧数据。解决：`docker compose down -v` 后重新启动。

### 问题 4：语义缓存不生效

**症状**：相似问题每次都调用 LLM

**排查**：

- 确认 Redis 运行正常：`docker compose exec redis redis-cli ping` 应返回 `PONG`。
- 检查 `REDIS_CACHE_THRESHOLD` 是否过高（默认 0.92 已经很严格）。
- 确认 `REDIS_URL` 指向正确的 Redis 实例。

### 问题 5：CORS 错误

**症状**：前端请求被浏览器拦截

**解决**：修改 `.env` 中的 `CORS_ORIGINS`，添加前端的实际域名：

```env
CORS_ORIGINS=http://localhost:3000,http://localhost:5173,https://your-domain.com
```

### 问题 6：文件上传失败（413 错误）

**解决**：增大 `FILE_UPLOAD_MAX_MB` 的值（默认 2MB）。

### 问题 7：LightRAG 查询无结果

**排查**：

1. 确认 `LIGHTRAG_WORKING_DIR` 目录下有数据文件（`docker compose exec backend ls -la ./data/lightrag/`）。
2. 如果目录为空，可能是构建时未初始化。设置 `INIT_LIGHTRAG_ON_BUILD=true` 并重新构建。
3. 确认 `LIGHTRAG_ENABLE_NEO4J=True` 且 Neo4j 正常运行。

## 9.8 线上化风险与建议

### 风险清单

| 风险 | 严重程度 | 说明 |
|---|---|---|
| API Key 泄露 | 高 | `.env` 文件不应提交到 Git。`docker-compose.yml` 中的 build args 会在构建日志中显示。 |
| 无鉴权 | 高 | 后端 API 无认证机制，任何人可以调用。上线前必须加鉴权层。 |
| 单点故障 | 高 | 所有服务单实例运行，任一服务崩溃即整体不可用。 |
| 无限流 | 中 | 无请求频率限制，恶意用户可以耗尽 LLM API 额度。 |
| 数据未加密 | 中 | 数据库连接使用明文密码，Redis 无密码。 |
| 日志敏感信息 | 中 | 开启 `DEBUG=True` 时日志可能包含用户输入和 API 响应。 |
| 资源无上限 | 中 | `MAX_ITERATIONS=10` 和 `AGENT_TIMEOUT=300` 防止无限循环，但单次请求仍可能消耗大量 token。 |

### 上线建议

1. **关闭调试模式**：`DEBUG=False`
2. **添加 API 鉴权**：在 FastAPI 层加 JWT 或 API Key 校验中间件
3. **使用密钥管理**：不要把 API Key 写在 `.env` 文件中，改用 Docker Secrets 或云厂商的密钥管理服务
4. **前置 Nginx 反向代理**：处理 SSL 终止、限流、静态文件缓存
5. **配置 Gunicorn 多 Worker**：`gunicorn -c gunicorn.conf.py gustobot.main:application`，生产环境用 4+ 个 Worker
6. **数据库密码轮换**：修改 MySQL、Neo4j、Redis 的默认密码
7. **监控与告警**：接入 Prometheus + Grafana，监控 LLM 调用延迟、缓存命中率、错误率
8. **日志脱敏**：生产环境关闭 DEBUG，确保日志不包含用户隐私数据
9. **备份策略**：定期备份 MySQL（`mysqldump`）、Neo4j（`neo4j-admin dump`）、Milvus 数据卷
10. **资源限制**：在 `docker-compose.yml` 中为每个服务设置 `deploy.resources.limits`，防止 OOM
