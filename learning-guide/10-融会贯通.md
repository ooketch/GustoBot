**7 种路由类型的决策逻辑详解**：

| # | Router.type | 触发条件 | 目标节点 | 数据源 | 典型问题 |
|---|------------|---------|---------|--------|---------|
| 1 | `general-query` | 问候、寒暄、情绪 | `respond_to_general_query` | LLM 直接生成 | "你好"、"谢谢" |
| 2 | `additional-query` | 模糊、缺关键词 | `get_additional_info` | Guardrails + LLM | "我想做菜" |
| 3 | `kb-query` | 历史、典故、文化 | `create_kb_query` | Milvus + PostgreSQL | "宫保鸡丁的历史" |
| 4 | `graphrag-query` | 做法、食材、步骤 | `create_research_plan` → KG 子图 | Neo4j + LightRAG | "红烧肉怎么做" |
| 5 | `text2sql-query` | 统计、多少、排名 | `create_research_plan` → KG 子图 | MySQL | "有多少道菜" |
| 6 | `image-query` | 图片关键词 | `create_image_query` | Vision API / CogView-4 | "生成一张图" |
| 7 | `file-query` | 上传文件 | `create_file_query` | 文件系统 + KB | "分析这个菜谱" |

**关键设计决策**：
- `graphrag-query` 和 `text2sql-query` 共享同一个入口节点 `create_research_plan`，通过 `route_type` 参数区分工具选择
- 启发式路由器 `_heuristic_router` (`lg_builder.py:986`) 作为 LLM 路由的 fallback，包含关键词匹配
- 图片和文件路由优先级最高：如果 `config` 中有 `image_path` 或 `file_path`，直接覆盖 LLM 的路由结果 (`lg_builder.py:214-220`)

## 二、三个典型问题的完整代码追踪

### 追踪 1："宫保鸡丁怎么做" → graphrag-query → KG 子图 → Predefined Cypher → Neo4j

**Step 1：API 入口**
- 文件：`gustobot/interfaces/http/v1/chat.py`
- 函数：`chat()` (第 244 行)
- 入参：`ChatRequest { message: "宫保鸡丁怎么做", session_id: "xxx" }`
- 调用 `get_or_create_session()` 创建/获取会话
- 调用 `save_message()` 保存用户消息到 PostgreSQL
- 调用 `process_agent_query()` 进入 Agent 层

**Step 2：主图路由**
- 文件：`gustobot/application/agents/lg_builder.py`
- 函数：`analyze_and_route_query()` (第 103 行)
- 构建 `ChatOpenAI` 实例（第 122 行），使用 `settings.OPENAI_MODEL`
- 将 `ROUTER_SYSTEM_PROMPT` + 用户消息发送给 LLM
- LLM 结构化输出 `Router(type="graphrag-query", logic="用户询问菜品做法")`
- 返回 `{"router": Router(...)}`

**Step 3：条件路由**
- 文件：`gustobot/application/agents/lg_builder.py`
- 函数：`route_query()` (第 197 行)
- `_type = "graphrag-query"`
- 匹配条件 `_type in ("graphrag-query", "text2sql-query")` (第 227 行)
- 返回 `"create_research_plan"`

**Step 4：创建研究计划**
- 文件：`gustobot/application/agents/lg_builder.py`
- 函数：`create_research_plan()` (第 804 行)
- 获取 Neo4j 连接：`get_neo4j_graph()` (第 834 行)
- 创建 Cypher 示例检索器：`RecipeCypherRetriever()` (第 840 行)
- 定义工具 schema 列表（第 849-854 行）：`[cypher_query, predefined_cypher, microsoft_graphrag_query, text2sql_query]`
- 创建 KG 子图：`create_multi_tool_workflow(...)` (第 888 行)
- 准备输入状态（第 901 行）：`{ question: "宫保鸡丁怎么做", data: [], history: [], route_type: "graphrag-query" }`
- 执行子图：`multi_tool_workflow.ainvoke(input_state)` (第 909 行)

**Step 5：KG 子图 -- Guardrails**
- 文件：`gustobot/application/agents/kg_sub_graph/agentic_rag_agents/components/guardrails/node.py`

## 三、常见追问清单及参考回答

### Q1：主图和子图的关系是什么？为什么要嵌套？

**回答**：主图（`lg_builder.py` 的 `StateGraph`）负责意图路由，有 7 个叶子节点。其中 `create_research_plan` 和 `create_kb_query` 两个节点内部会各自创建一个独立的 `StateGraph`（即子图）。

嵌套的原因是关注点分离：
- **主图**关注"这个用户问题应该交给谁处理"（路由层）
- **KG 子图**关注"如何从知识图谱中高效检索"（Guardrails → Planner → Tool Selection → Tool → Summarize）
- **KB 子图**关注"如何从向量知识库中检索并融合"（Guardrails → Router → Local/External Search → Finalize）

子图有自己的 state 类型（`OverallState`、`KBWorkflowState`），与主图的 `AgentState` 独立，通过函数返回值桥接。

### Q2：LangGraph 的 Map-Reduce 模式是怎么实现的？

**回答**：在 KG 子图中：
1. **Map**：`planner` 节点将用户问题分解为多个 `Task`，写入 `state["tasks"]`
2. **Fan-out**：`map_reduce_planner_to_tool_selection()`（`edges.py`）遍历每个 Task，为每个 Task 发出一个 `Send("tool_selection", ...)` 消息
3. **并行执行**：每个 `tool_selection` 实例独立运行，通过 `Command(goto=Send(...))` 路由到对应的工具节点
4. **Reduce**：所有工具节点的结果通过 `Annotated[List, add]` reducer 自动合并到 `cyphers` 列表中
5. **汇聚**：`summarize` 节点读取合并后的 `cyphers` 列表，统一格式化

这是 LangGraph 的原生 Map-Reduce 模式，通过 `Send` 和 reducer 实现无锁并行。

### Q3：7 种路由类型中，graphrag-query 和 text2sql-query 为什么共享同一个入口？

**回答**：因为它们都需要访问结构化数据源（Neo4j/MySQL），且都需要经历相同的 Guardrails → Planner → Tool Selection 流程。区别仅在于 Tool Selection 阶段：
- `graphrag-query` → Planner 选择 `predefined_cypher` 或 `cypher_query` 或 `microsoft_graphrag_query`
- `text2sql-query` → Tool Selection 的启发式检查直接路由到 `text2sql_query`

通过 `route_type` 参数传递到子图，Tool Selection 节点根据这个参数调整决策逻辑。这种设计避免了代码重复。

### Q4：KB 子图中 PostgreSQL 优先于 Milvus 的策略是什么？

**回答**：在 `local_search()` 函数（`multi_tool.py:554`）中实现了明确的优先级策略：
1. 如果 `postgres` 在工具列表中，先查询 PostgreSQL
2. 如果 PostgreSQL 返回结果（>= 1 条），直接使用，**跳过 Milvus 查询**
3. 如果 PostgreSQL 无结果或不可用，才降级到 Milvus 兜底
4. 如果两者都无结果，且允许外部搜索，自动切换到 `external_search`

PostgreSQL 存放结构化表格数据（Excel 导入的枚举字段），数据更准确、查询更快；Milvus 存放长文本、文章、典故故事等非结构化内容，作为兜底。

### Q5：系统有哪些降级/容错机制？

**回答**：
1. **路由降级**：LLM 路由失败 → `_heuristic_router()` 关键词匹配 → 默认 `kb-query`（`lg_builder.py:138-143, 158-159`）
2. **类型校验**：Router 返回非法 type → 启发式 fallback → 默认 `kb-query`（`lg_builder.py:165-181`）
3. **子图 Guardrails**：KG 子图和 KB 子图都有独立的 Guardrails 节点，检查问题是否在范围内
4. **工具选择降级**：LLM 不返回工具选择 → 默认 `cypher_query`（Text2Cypher）
5. **KB 多源降级**：PostgreSQL 无结果 → Milvus 兜底 → 外部搜索兜底
6. **KB 工作流降级**：`create_kb_query()` 中 KB 子图异常 → 降级到直接 `KnowledgeService.search()`（`lg_builder.py:783-801`）
7. **LLM 调用失败**：Guardrails LLM 失败 → 默认放行（`planner`）

### Q6：状态是怎么在主图和子图之间传递的？

**回答**：
- **主图 → 子图**：函数调用时显式构造输入状态。例如 `create_research_plan()` 构造 `input_state = { question, data, history, route_type }`，然后调用 `multi_tool_workflow.ainvoke(input_state)`
- **子图 → 主图**：函数返回值。子图的 `OutputState` 被 LangGraph 提取后，由父函数读取。例如 `response = await multi_tool_workflow.ainvoke(input_state)`，然后 `return {"messages": [AIMessage(content=response["answer"])]}`
- 主图的 `AgentState` 和子图的 `OverallState` / `KBWorkflowState` 是完全独立的 TypedDict，通过函数调用边界解耦

### Q7：Tool Selection 节点的启发式快速路径是什么？

**回答**：在 `tool_selection/node.py` 中，LLM 调用之前有两层启发式检查：
1. **描述性关键词检查**：如果问题包含口味、食材、营养、功效等关键词（`DESCRIPTIVE_KEYWORDS`），直接路由到 `customer_tools`（LightRAG），跳过 LLM
2. **SQL 模式检查**：如果问题匹配 SQL 模式（`SQL_PATTERN`）或包含 SQL 关键词，且 `route_type == "text2sql-query"`，直接路由到 `text2sql_query`

这层启发式的作用是减少 LLM 调用次数，提高响应速度，同时避免 LLM 选错工具。

## 四、项目亮点总结（可以写进简历的）

### 亮点 1：多层级 Agent 路由架构

> 设计并实现了 7 种路由类型的智能 Agent 系统，基于 LangGraph StateGraph 构建主图 + 两个子图的嵌套架构。主图负责意图分类和路由分发，子图负责具体的知识检索和推理。实现了 LLM 路由 + 启发式 fallback 的双重保障机制。

### 亮点 2：Map-Reduce 并行工具调用

> 在 KG 子图中实现了 Planner → Map-Reduce → Tool Selection → 多工具并行执行的流水线。通过 LangGraph 的 `Send` 原语和 `Annotated[List, add]` reducer 实现无锁并行，支持 predefined_cypher、text2cypher、LightRAG、text2sql 四种工具的自动选择和并行执行。

### 亮点 3：多源知识融合（RAG + KG + SQL）

> 系统同时对接 Neo4j 图数据库、MySQL 关系数据库、Milvus 向量数据库、PostgreSQL pgvector 四种数据源，以及 LightRAG 图推理引擎。通过 Planner 动态选择最优工具组合，通过 Summarize 节点融合多源结果生成统一回答。

### 亮点 4：多级降级容错体系

> 实现了从路由层到工具层的完整降级链路：LLM 路由失败 → 关键词启发式 → 默认 KB 路由；KB 子图异常 → 直接向量检索；PostgreSQL 无结果 → Milvus 兜底 → 外部搜索。系统在任何单点故障下都不会崩溃。

### 亮点 5：结构化输出驱动的 Agent 决策

> 全链路使用 Pydantic BaseModel + `with_structured_output()` 实现 LLM 的结构化决策：Router 分类、Guardrails 审查、Tool Selection 工具选择、Planner 任务分解、Text2Cypher/Text2SQL 生成。避免了自由文本解析的脆弱性。

### 亮点 6：PostgreSQL 优先 + Milvus 兜底的检索策略

> 设计了 PostgreSQL pgvector 优先、Milvus 向量库兜底的双源检索策略。结构化数据走 PostgreSQL（更快、更准），非结构化长文本走 Milvus。通过 Reranker 多阶段重排序保证检索精度。

### 亮点 7：完整的多模态能力

> 支持文本问答、图片识别（Vision API）、图片生成（CogView-4）、文件导入（txt/md/json/csv/Excel）四种交互模态，通过统一的 `/api/v1/chat/` 端点接入，由路由层自动分发。

## 五、项目局限性和改进方向

### 局限 1：子图之间无法并行

**现状**：主图的 7 个叶子节点是串行执行的（一个请求只走一条路径）。如果用户同时问"宫保鸡丁怎么做"和"它的历史典故"，需要两次独立请求。

**改进方向**：支持单次请求的多意图拆分，让 graphrag-query 和 kb-query 可以并行执行后合并结果。

### 局限 2：对话历史管理粗糙

**现状**：主图使用 `MemorySaver` 作为 checkpointer（`lg_builder.py:955`），会话历史存在内存中，服务重启后丢失。KG 子图使用滑动窗口（最近 5 条），KB 子图只传递最近 4 条历史。

**改进方向**：将 checkpointer 替换为 `PostgresCheckpointer` 或 `RedisCheckpointer`，实现持久化会话管理。

### 局限 3：Tool Selection 的启发式规则硬编码

**现状**：`tool_selection/node.py` 中的 `DESCRIPTIVE_KEYWORDS` 和 `SQL_PATTERN` 是硬编码的，覆盖范围有限。新增数据源或查询类型时需要手动修改。

**改进方向**：将启发式规则配置化，或用 few-shot examples 训练一个轻量级分类器替代硬编码规则。

### 局限 4：Summarize 节点未使用 LLM

**现状**：`summarize/node.py` 中准备了 LLM chain（`generate_summary_prompt | llm | StrOutputParser`），但当前实现直接从结构化数据拼接摘要，LLM chain 未被调用。

**改进方向**：启用 LLM-based 摘要生成，提升回答的自然度和可读性，特别是多工具结果融合时。

### 局限 5：缺少评估和可观测性

**现状**：系统有日志（`loguru`），但缺少结构化的 trace/metrics 采集。无法量化路由准确率、工具选择准确率、端到端延迟分布。

**改进方向**：集成 LangSmith 或 OpenTelemetry，实现全链路 trace 和关键指标的自动采集。

### 局限 6：Text2SQL 的 schema 依赖 Neo4j

**现状**：`create_text2sql_tool_node()` 需要一个 Neo4j 连接来获取数据库 schema（`text2sql_tool.py`）。这意味着即使只做 SQL 查询，也必须有 Neo4j 可用。

**改进方向**：将 schema 信息缓存到本地或独立的服务中，解耦 Text2SQL 对 Neo4j 的依赖。

### 局限 7：流式响应是模拟的

**现状**：`stream_agent_response()`（`chat.py:185`）先等待完整结果，再逐词发送 SSE 事件。不是真正的 token-by-token 流式。

**改进方向**：使用 LangGraph 的 `astream_events()` API 实现真正的 token 流式传输，降低首 token 延迟。
