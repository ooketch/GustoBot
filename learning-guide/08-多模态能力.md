## 8.1 全景概览：多模态在 LangGraph 中的位置

GustoBot 的多模态能力并非独立模块，而是深度嵌入 LangGraph 工作流。核心路由逻辑在 `lg_builder.py` 的 `route_query` 函数中：

```python
# lg_builder.py -- route_query() 片段
if hasattr(state, "config") and state.config:
    cfg = state.config.get("configurable", {})
    if cfg.get("image_path"):
        return "create_image_query"
    if cfg.get("file_path"):
        return "create_file_query"
```

这段代码说明了一个关键设计：**`image_path` 和 `file_path` 作为 configurable 参数，优先级高于路由器的 LLM 分类结果**。也就是说，只要上游传入了图片或文件路径，就直接跳转到对应的处理节点，不再经过意图识别。

StateGraph 中注册的节点和边：

```
START --> analyze_and_route_query --> [条件分支]
    |--> respond_to_general_query
    |--> get_additional_info
    |--> create_research_plan
    |--> create_image_query      <-- 图片识别 / 图片生成
    |--> create_file_query       <-- 文件处理
    |--> create_kb_query
```

## 8.2 文件上传接口

### 8.2.1 接口定义

文件位于 `gustobot/interfaces/http/v1/upload.py`，提供以下 REST 接口：

| 方法 | 路径 | 功能 |
|------|------|------|
| `POST` | `/api/v1/upload/file` | 上传文件 |
| `POST` | `/api/v1/upload/image` | 上传图片 |
| `GET` | `/api/v1/upload/files/{filename}` | 下载已上传的文件 |
| `GET` | `/api/v1/upload/images/{filename}` | 下载已上传的图片 |
| `DELETE` | `/api/v1/upload/{file_id}` | 删除已上传的文件 |

### 8.2.2 支持的文件格式

代码中通过两个白名单常量严格限制：

```python
# 普通文件
ALLOWED_FILE_TYPES = {
    '.txt', '.md', '.json', '.csv', '.log', '.xlsx', '.xls', '.pdf', '.doc', '.docx'
}

# 图片文件
ALLOWED_IMAGE_TYPES = {
    '.jpg', '.jpeg', '.png', '.gif', '.bmp', '.webp'
}
```

### 8.2.3 存储方式

- **存储位置**：普通文件存入 `uploads/` 目录，图片存入 `uploads/images/` 子目录
- **文件命名**：使用 `uuid4()` 生成唯一 ID，拼接原始文件名，格式为 `{uuid}_{原始文件名}`，避免重名冲突
- **大小限制**：`MAX_FILE_SIZE = 50 * 1024 * 1024`（50MB），在内存中读取后判断大小
- **异步写入**：使用 `aiofiles` 库进行异步文件 I/O，不阻塞事件循环

上传成功后返回的 JSON 结构：

```json
{
    "success": true,
    "file_id": "uuid-string",
    "filename": "uuid_original.xlsx",
    "original_name": "original.xlsx",
    "size": 12345,
    "file_path": "uploads/uuid_original.xlsx",
    "file_url": "/api/v1/upload/files/uuid_original.xlsx",
    "file_type": ".xlsx"
}
```

图片接口返回结构类似，额外提供 `image_id` 和 `image_url` 字段。

## 8.3 图片识别（Vision Model）

### 8.3.1 触发条件

在 `create_image_query` 函数中，系统通过两个条件判断是"识别"还是"生成"：

```python
generation_keywords = ["生成", "画", "创建", "制作图片", "做一张", "给我一张", "来一张"]
is_generation = any(keyword in user_query for keyword in generation_keywords)

if is_generation and not image_path:
    return await _generate_image(user_query, state)
```

简单来说：**有图片路径就识别，没有图片路径但包含生成关键词就生成**。

### 8.3.2 图片预处理流程

识别前对图片做三步压缩，保证 API 调用效率：

```python
with Image.open(image_path) as img:
    # 1. 等比缩放，最大边 1024px
    max_size = 1024
    ratio = min(max_size / width, max_size / height)
    if width <= max_size and height <= max_size:
        resized_img = img
    else:
        resized_img = img.resize((new_width, new_height), Image.LANCZOS)

    # 2. 统一转为 RGB 模式（处理 RGBA/P 等格式）
    if resized_img.mode != 'RGB':
        resized_img = resized_img.convert('RGB')

    # 3. JPEG 压缩，quality=85
    resized_img.save(img_byte_arr, format='JPEG', quality=85)

    # 4. Base64 编码
    image_data = base64.b64encode(img_byte_arr.read()).decode('utf-8')
```

关键决策说明：
- 使用 `Image.LANCZOS` 重采样算法，它是高质量缩小的业界标准
- `quality=85` 在视觉质量和传输大小之间取平衡
- 强制转 RGB 是因为 JPEG 不支持透明通道

### 8.3.3 Vision API 调用方式

通过 `aiohttp` 直接发送 HTTP 请求到 OpenAI 兼容的 Vision API：

```python
payload = {
    "model": vision_model,          # settings.VISION_MODEL
    "messages": [
        {
            "role": "system",
            "content": "你是一个专业的菜谱图像分析助手..."
        },
        {
            "role": "user",
            "content": [
                {
                    "type": "image_url",
                    "image_url": {
                        "url": f"data:image/jpeg;base64,{image_data}"
                    }
                }
            ]
        }
    ],
    "max_tokens": 4000,
    "temperature": 0.7
}
```

注意：这里使用的是 **OpenAI Vision API 的标准格式** -- `content` 为数组，包含 `type: "image_url"` 的对象，图片数据以 Data URL 形式内嵌。

### 8.3.4 两阶段回复

Vision API 返回图片描述后，并不直接返回给用户，而是进入第二阶段：

1. **第一阶段**：Vision Model 生成图片的结构化描述
2. **第二阶段**：将描述注入 `GET_IMAGE_SYSTEM_PROMPT` 模板，交由主 LLM 生成面向用户的菜谱风格回复

```python
system_prompt = GET_IMAGE_SYSTEM_PROMPT.format(image_description=image_description)
messages = [{"role": "system", "content": system_prompt}] + state.messages
response = await model.ainvoke(messages)
```

这种两阶段设计的好处是：Vision Model 专注于"看"，主 LLM 专注于"说"，职责分离。

## 8.4 图片生成（CogView-4）

### 8.4.1 Prompt 增强

直接把用户的话扔给图片生成模型效果往往不好。GustoBot 先用 LLM 做一次 Prompt 增强：

```python
enhance_prompt = IMAGE_GENERATION_ENHANCE_PROMPT.format(user_query=user_query)
enhanced_response = await model.ainvoke(enhance_messages)
enhanced_prompt = enhanced_response.content.strip()
```

增强 Prompt 的要求（来自 `lg_prompts.py`）：
- 保留核心内容（菜品名称等）
- 丰富细节：色彩、质感、光影、摆盘
- 使用商业美食摄影的专业描述
- 控制长度在 50-150 字

### 8.4.2 CogView-4 API 调用

CogView-4 是智谱 AI 的图片生成模型，通过标准 REST API 调用：

```python
api_url = f"{base_url}/images/generations"
payload = {
    "model": model_name,           # settings.IMAGE_GENERATION_MODEL = "cogView-4-250304"
    "prompt": enhanced_prompt,
    "size": size                   # settings.IMAGE_GENERATION_SIZE = "1024x1024"
}
```

默认配置指向智谱 AI 的开放平台：`https://open.bigmodel.cn/api/paas/v4`。

### 8.4.3 菜名提取与格式化

生成成功后，系统会尝试从用户问题中提取菜名，用于格式化回复：

```python
dish_name = "菜品"
for keyword in ["宫保鸡丁", "红烧肉", "麻婆豆腐", "糖醋排骨", "鱼香肉丝"]:
    if keyword in user_query:
        dish_name = keyword
        break
```

这是一个简化实现，只匹配了几个常见菜名。实际生产中可以接入 NER 模型或菜谱知识库做更准确的提取。

## 8.5 文件处理（create_file_query）

### 8.5.1 分支策略

文件处理的核心逻辑是**按文件类型走不同处理路径**：

```python
# Excel 文件 -> 外部 Ingest 服务
if suffix in {".xlsx", ".xls"}:
    # POST 到 INGEST_SERVICE_URL/api/ingest/excel

# 文本类文件 -> 本地 KnowledgeService
elif suffix in {".txt", ".md", ".csv", ".log"}:
    raw_text = p.read_text(encoding="utf-8", errors="ignore")
elif suffix == ".json":
    data = json.loads(p.read_text(...))
    raw_text = json.dumps(data, ensure_ascii=False, indent=2)

# 其他格式 -> 拒绝
else:
    return "暂不支持该文件类型"
```

### 8.5.2 Excel 走外部 Ingest 服务

Excel 文件结构复杂，不适合直接读取文本，因此交给专门的外部服务处理：

```python
payload = {
    "excel_path": str(p),
    "incremental": incremental_flag,   # 是否增量导入
    "regenerate": regenerate_flag,     # 是否重新生成
}
async with session.post(
    f"{ingest_service_url.rstrip('/')}/api/ingest/excel",
    json=payload,
    timeout=60,
) as resp:
```

相关配置项：
- `INGEST_SERVICE_URL`：外部 Ingest 服务的基础 URL
- `INGEST_INCREMENTAL_DEFAULT`：是否默认增量导入（默认 `True`）

### 8.5.3 TXT/MD/JSON 走 KnowledgeService

文本类文件直接读取内容，通过 `KnowledgeService.add_document` 写入向量知识库：

```python
doc_id = f"upload_{p.stem}_{uuid.uuid4().hex[:6]}"
title = p.stem
success = await service.add_document(
    doc_id=doc_id,
    title=title,
    content=raw_text,
    metadata={"category": "uploaded"},
)
```

写入成功后，还会立即用 `create_knowledge_query_node` 做一次检索，返回与文件内容相关的初步摘要。

### 8.5.4 文件大小限制

代码中使用 `settings.FILE_UPLOAD_MAX_MB`（默认 2MB）限制文件大小：

```python
if size_bytes > settings.FILE_UPLOAD_MAX_MB * 1024 * 1024:
    return {"messages": [AIMessage(content=f"文件过大（>{settings.FILE_UPLOAD_MAX_MB}MB），请分割后重新上传。")]}
```

注意：上传接口的 `MAX_FILE_SIZE` 是 50MB（面向 HTTP 层），而 `FILE_UPLOAD_MAX_MB` 是 2MB（面向业务层）。两层校验各司其职。

## 8.6 image_path / file_path 参数怎么和路由关联

这是理解多模态流程的关键问题。整个链路如下：

### 8.6.1 前端上传

1. 用户通过 `/api/v1/upload/file` 或 `/api/v1/upload/image` 上传文件
2. 服务端保存文件到 `uploads/` 目录，返回 `file_path`（如 `uploads/uuid_name.xlsx`）

### 8.6.2 前端发起对话

前端在发送聊天消息时，将 `file_path` 或 `image_path` 放入 LangGraph 的 `configurable` 参数中：

```python
config = {
    "configurable": {
        "thread_id": "xxx",
        "image_path": "uploads/images/uuid_photo.jpg",  # 或
        "file_path": "uploads/uuid_doc.xlsx"
    }
}
```

### 8.6.3 路由优先级

在 `route_query` 中，**configurable 中的路径参数优先于 LLM 路由器的分类结果**：

```python
# 先检查 configurable
if cfg.get("image_path"):
    return "create_image_query"
if cfg.get("file_path"):
    return "create_file_query"

# 再看 LLM 路由器的分类
if _type == "image-query":
    return "create_image_query"
```

这意味着即使用户说"帮我看看这张图"但没有传 `image_path`，路由器会分类为 `image-query`，但 `create_image_query` 会因为找不到文件而返回错误提示。

## 8.8 多模态失败时的降级策略

GustoBot 在多模态链路的每个环节都做了异常处理，确保不会因为某个服务不可用而崩溃：

### 8.8.1 图片识别降级

| 失败场景 | 降级行为 |
|----------|----------|
| `image_path` 为空 | 返回 "抱歉，我无法查看这张图片，请重新上传。" |
| 文件不存在 | 同上 |
| Vision API 配置不完整（缺 key/url/model） | 同上 |
| Vision API 返回非 200 | 同上 |
| 图片处理异常（PIL 无法打开等） | 捕获通用 Exception，返回同样的错误提示 |

### 8.8.2 图片生成降级

| 失败场景 | 降级行为 |
|----------|----------|
| `IMAGE_GENERATION_API_KEY` 未配置 | 返回 "图片生成服务配置不完整" |
| API 返回非 200 | 返回 "图片生成失败，请稍后再试" |
| 响应中无图片数据 | 同上 |
| 请求超时（60秒） | 返回 "图片生成超时，请稍后再试" |
| 通用异常 | 返回具体错误信息 |

### 8.8.3 文件处理降级

| 失败场景 | 降级行为 |
|----------|----------|
| `file_path` 为空 | 返回 "请提供要处理的文件路径。" |
| 文件不存在 | 返回 "未找到该文件，请确认路径是否正确。" |
| 文件过大 | 返回文件大小超限提示 |
| Excel 处理但 `INGEST_SERVICE_URL` 未配置 | 返回 "未配置外部接入服务，无法处理 Excel 导入。" |
| 外部服务返回错误 | 返回 HTTP 状态码和错误文本 |
| KnowledgeService 保存失败 | 返回 "文件已读取，但保存到知识库失败" |
| 不支持的文件类型 | 返回 "暂不支持该文件类型" |

所有降级策略的共同特点是：**捕获异常 -> 记录日志 -> 返回友好的中文错误消息**，不会让异常传播到上层导致整个请求崩溃。

## 8.9 完整数据流：以图片识别为例

```
用户上传图片
    |
    v
POST /api/v1/upload/image
    |-- 保存到 uploads/images/{uuid}_{filename}
    |-- 返回 { image_path, image_url, ... }
    |
    v
用户发送消息（附带 image_path）
    |
    v
analyze_and_route_query（意图识别）
    |
    v
route_query（路由判断）
    |-- 检测到 configurable.image_path -> create_image_query
    |
    v
create_image_query
    |-- 判断：无生成关键词 + 有 image_path -> 走识别流程
    |-- PIL 打开图片 -> 缩放到 1024px -> 转 RGB -> JPEG 压缩
    |-- Base64 编码
    |-- 调用 Vision API（data:image/jpeg;base64,...）
    |-- 获取图片描述
    |-- 注入 GET_IMAGE_SYSTEM_PROMPT
    |-- 调用主 LLM 生成菜谱风格回复
    |
    v
返回 AI 消息给用户
```
